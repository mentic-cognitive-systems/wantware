Wantware

Hardware executes physics.
Software executes logic.
Wantware executes purpose.

Software is a layer built on hardware, with a product of its own (programs) and a process of its own (write, compile, run). Wantware is the next layer, built on software. Its product is a want held as a precise, versioned contract. Its process turns that contract into software and then checks the running result against the original want.

The analogy

One layer up

Each layer in computing gave people something new to write down. Hardware made physics compute. Software let people write behavior as text instead of wiring it into circuits. The instruction set was the contract that made this work: write to it, and any machine that honors it will run your program.

Wantware makes the same move one layer up. It lets people write down what they want, precisely enough to version it, check it, and build from it. Its contract with the layer below is a set of capabilities, such as readEmail, rather than particular code. Any implementation that provides the capability will do: the Gmail API today, IMAP tomorrow, a test fixture during validation.

Software did not replace circuit design, and wantware does not replace software engineering. Below the code boundary, ordinary engineering stays in charge. Wantware's new work happens above it, where a want is captured, read, given exact meaning, and designed for.

Wantware as a process

Seven transformations, from want to running machinery

Software's process has three verbs: write, compile, run. Wantware keeps them as its bottom three stages and adds four above them. The stages are kinds of transformation, not a document waterfall. One element of a system can be confirmed while its neighbor is still a rough idea, and each element carries its own stage, version, and provenance.

When it fails, the question climbs

Suppose the system above runs perfectly and the user still misses something important, because it arrived in Slack. Every tool call succeeded. Wantware asks, one boundary at a time, which layer explains the failure, and repairs at the lowest one that does.

  1. ComputationDid the machinery run incorrectly?No
  2. CompilationWas the executable built incorrectly?No
  3. CodificationDoes the source misimplement the design?No
  4. CognificationDoes the mechanism fail to satisfy the contract?No
  5. FormalizationIs the contract wrong or incomplete? Slack messages were never part of the modeled world.Yes
  6. ConceptualizationWas the want read incorrectly?Not reached
  7. ConceptionWas the want itself incoherent?Not reached

This is a semantic failure, and no amount of perfect execution repairs it. The Cognifier cannot quietly add Slack. It sends a typed semantic-change-required return to the Formalizer, who takes it to the client. Once the client confirms, the contract becomes a new version, and only the elements that depend on the change flow back down. Everything else stays as built.

Who may change what

Three authorities sit between the want and the code, and none may silently rewrite another. A role that finds a defect upstream returns a typed issue to the owner; it does not patch the owner's work. One person or model can play several roles. The role it is acting in decides what it may change.

“Users should be able to recover their account without compromising their encrypted data.”

The Formalizer asks

What is an account? What counts as recovery? Which security properties make up “without compromising”? What evidence would show a recovery worked?

The Cognifier asks

Recovery key, trusted devices, secret sharing, or escrow? What are the failure modes? What procedure takes a user from locked out to recovered?

The Codifier asks

Which types, modules, schema, APIs, and tests express the mechanism that was chosen?

The thread of obligations

Running through all seven stages is a sequence of speech acts. It records who asked, what is true now, what must become true, who promised to deliver it, and who gave the instructions. A confirmed contract is not a promise to deliver it, and a finished instruction list is not proof the want was met.

  1. ExpressiveStates the want and why it matters“I want a reliable daily operational digest.”
  2. AssertiveEstablishes the current and wanted state, keeping evidence apart from assumption“Updates are spread across three systems. The team wants one accurate digest by 9 a.m. each workday.”
  3. DeclarativeSays what must become true to close the gap“The digest covers all three systems, names its sources, flags missing data, and is ready by 9 a.m.”
  4. CommissiveAn accountable actor promises delivery, with scope and conditions“I commit to delivering that digest under these conditions.”
  5. DirectiveThe one who committed writes the work instructions“Collect the updates, reconcile them, validate against the acceptance conditions, publish.”
  6. ImperativeConcrete steps a machine can execute“Fetch each source; normalize; summarize; check coverage; publish; record the result.”
  7. ↺ EvidenceChecks the result against the declaratives and the original wantA mismatch is recorded as an unmet commitment and re-enters the right stage. The want is never redefined to fit what was produced.

Evidence decides

tool returned≠operation succeeded≠desired state achieved

Completion is a property of recorded state, not of a model's confidence. A claim counts as established only when the observations its satisfaction case requires have been acquired, and the reasoning that links those observations to the claim, its warrant, holds up.

{
  "action":    "create_record",
  "transport": { "status": "success" },
  "evidence":  { "recordsCreated": 0 },
  "expected":  { "recordsCreated": 1 },
  "semanticOutcome": "FAILED"
}

Knowledge is recorded on two separate axes, so “no data” never quietly turns into a guess. An empty calendar and a failed calendar query look alike to a model filling gaps. Here they are different records.

Wantware as a product

What gets made, and what you keep

Software ships in two forms: the source you keep and change, and the executable the machine runs. The executable is derived. If you lose it, you rebuild it from source.

Wantware has the same split, one layer up. What you keep is the want, formalized and versioned, together with the mechanism designed for it. What runs is the software derived from that. The code becomes the derived form, the way a binary is.

The kept form is the WantwareIR: one versioned graph with four strata, each owned by a different authority. Every stratum binds the exact version and content hash of the one above it, so when something upstream changes, what has gone stale is visible instead of implied.

“Source” here means the source of intent, not source code.

SOURCEclient · interpreterThe want, verbatim, and the recorded reading of it

Portable

The semantic and cognitive strata name no implementation, so one confirmed snapshot can be codified into several ecosystems. This is the instruction-set idea again, one layer up.

Self-checking

Source, tests, validators, and runtime telemetry requirements all derive from the same contract. The product carries its own definition of done, and running it produces the evidence to judge it.

Incremental

An incomplete IR is a valid artifact. Each element has its own version and lifecycle, and readiness is judged per handoff, so a change reopens only what depends on it.

It gets cheaper the more it runs

Each time a kind of want is worked all the way down, the reasoning it needed can be turned into ordinary machinery. “Whenever Mom emails about an appointment, put it on my calendar” costs expensive reasoning once: mapping the ontology, writing the procedure, testing a deterministic workflow. After that it runs as incoming email → compiled workflow → calendar event, with no model in the loop.

uncertain intention→reasoning→explicit concept→procedure→validated procedure→skill→guard→code→deterministic infrastructure

Failures compound the same way. A repeated mistake becomes a test, the test becomes a guard, and the guard becomes infrastructure. Every fuzzy judgment turned into a deterministic check is intelligence compiled into software.

The layer below went through this too. Work that software did constantly, such as video decoding and encryption, eventually moved into dedicated silicon. In wantware, reasoning that recurs moves into code.

Where it stands

Specified
The seven-stage model, the three authorities, and the evidence rules (Wantware.md). IR 0.3 and its JSON Schema (WantwareIR.md, WantwareIR.schema.json).
Proposed
Bringing the representation into the Agency's ACE³. The Architect acts as Cognifier and the Builder as Codifier. The Formalizer is a new role.
Implemented
Plan packages P1 and P2: the role renames, a new Integrator role between Builder and Validator, and evidence-based completion in kernel/evidence.js and kernel/wantware-ir.js. A task whose claims are not established now waits in awaiting_evidence instead of passing.
Not started
P0 (IR fixtures, the grammar decision, schema packaging), then P3 through P8.
Open gap
IR 0.3 has no record for the delivery commitment or for issuing Directives. For now these live in separate engagement records, bound to the exact contract and design versions.
Not designed yet
The intent language. It will be derived from three deliberately different encodings (MonyTyme, Trindex, MENTIC) instead of being designed up front.
